# PDF Layout Lab

## 범용 레이아웃 보존 점검 (2026-10-26)

분석 v17은 회전 및 CropBox를 포함한 PDF에서 분석·OCR 자르기·조판 좌표를 통일하고,
출력에서는 원본 페이지의 크기와 회전을 유지합니다. 화면의 영역 표시와 드래그 좌표도 변환합니다.
원본의 임의 방향 글자 자체를 재조판하는 기능과 페이지 `/Rotate` 처리는 별개입니다.

조판 v5는 특정 `Step` 문구 대신 정렬된 셀과 세로 글자 형상을 사용합니다. 대체 글꼴은
원본의 serif/sans-serif/monospace 계열과 굵기·기울임을 반영하며, 정확한 원본 글꼴 재사용은 보장하지 않습니다.
삭제 전 모든 FIT 영역에서 번역문 완전성·글자 경계·이웃 글자/그림/도형 충돌을 검사합니다.
배치 사각형이 겹쳐도 실제 글자와 지우기 범위가 안전하면 번역을 적용합니다.
네이티브 글자는 소유한 글자의 내부만 정밀 삭제할 수 있고, 스캔 패치는 지우는 부분만 불투명하게 만듭니다.
충돌은 빈 공간 안에서 재배치하며, 기존 삭제 주석은 실행하지 않습니다.

검증은 페이지 기하, 영역 밖 픽셀, 유지 영역 원문/서식, 원본 이미지·벡터,
링크 목적지, 주석 내용, 폼 값, 목차와 페이지 번호 체계를 비교합니다.
OCR가 없는 원본 이미지에 추출 텍스트가 없다는 이유로 누락 처리하지 않고 실제 원본 픽셀을 비교합니다.
OCR 엔진 오류는 페이지별 `analysis.diagnostics`에 기록하며 읽을 수 있는 다른 본문 처리를 계속합니다.

재현용 오프라인 검증:

```powershell
../backend/.venv/Scripts/python.exe -m pytest tests -q
node --test tests/test_geometry.cjs
../backend/.venv/Scripts/python.exe check_preservation.py ../output/pdf/layout-preservation
```

마지막 명령은 Poppler의 `pdftoppm`이 필요하며 다양한 PDF, 페이지별 비교 이미지와 JSON 보고서를 생성합니다.
`--saved-run RUN_DIRECTORY --source SOURCE_PDF`로 저장된 번역을 API 재호출 없이 검증할 수 있습니다.
원본과 기존 실행 폴더는 읽기만 합니다. 자세한 근거와 한계는
[점검 보고서](../docs/PDF_LAYOUT_PRESERVATION_AUDIT_2026-10-26.md)에 정리했습니다.

## 번역 우선 적용·검토·원문 복원 (2026-10-26 후속)

추가 수정: 검증 v4에서는 재배치 후에도 남는 영역 경계·겹침 위험을 **번역 적용 후 검토**로 처리합니다.
번역문 누락·페이지 밖 잘림·다른 원문 삭제·복잡한 배경 손상은 별도로 차단합니다.
같은 위치의 일반 텍스트/OCR 중복 기록은 한 번만 조판하며 수동 적용·복원도 함께 처리합니다.
원래 서식이 같은 표 내부 여러 줄의 글자 크기도 통일합니다.
서버 재시작 후 `/api/config`의 `render_version`이 4인지 확인할 수 있습니다. 이전 결과는 재생성이 필요합니다.

- `applied`와 `review_required`를 분리했습니다. 번역문이 들어간 상태에서도 가독성·재배치·이미지 경계를 검토할 수 있습니다. 단순 사각형 겹침만으로 미반영하거나 검토 표시하지 않습니다.
- `source_text`와 `translated_text`, 번역 단위와 원본 PDF를 별도로 보관합니다. **이 영역을 원문으로 복원**은 원본 PDF에서 해당 페이지를 다시 만들며, **보관된 번역문 다시 적용**으로 되돌릴 수 있습니다. 이전 실행은 유지합니다.
- `/render`의 `restore_region_ids`는 `base_run`으로 최신 실행을 확인합니다. 저장 정책의 `restored_regions`는 전체 재생성에도 복원 선택을 유지합니다. 번역 API는 호출하지 않습니다.
- 같은 표의 유사한 원본 크기·굵기·글꼴 계열·색상끼리 가능한 공통 크기를 적용합니다. 제목과 본문을 구별하며, 좁은 셀의 예외는 적용 후 검토 표시합니다.
- 검증 v3은 출력 glyph별 소속을 기록하고, 스캔 원문 유지 영역의 72dpi 경계 오차는 288dpi로 재검사합니다. 기존 구형 검증 보고서는 재사용하지 않습니다.
- 공간·인식·원문 보호 제약으로 실제 안전한 적용이 불가능하면 미반영 사유와 번역문을 함께 보관합니다. 페이지 전체 재흐름이나 무제한 글자 축소는 수행하지 않습니다.

실제 문서의 전후 수치와 남은 한계는 [후속 검증 보고서](../docs/PDF_TRANSLATION_PRIORITY_REVIEW_2026-10-26.md)를 참고하세요.

## Smart Export

입력: PDF, DOC, DOCX, HWP, HWPX, PPTX (25MB 이하). 기본 출력은 원본 형식입니다.

| 입력 | 원본 형식 번역 | 추가 Export |
|---|---|---|
| PDF | 기존 영역 번역 경로 | DOCX; 동일 크기 가로형 페이지는 PPTX 생성·렌더링 검증 후 제공 |
| DOCX | 원본 패키지 텍스트 교체 | PDF |
| PPTX | 원본 슬라이드 텍스트 교체 | PDF |
| HWPX | 원본 섹션 텍스트 교체, 줄 위치 캐시 재계산 | PDF, DOCX (변환 성공 시) |
| DOC, HWP | 현재 엔진은 원본 형식 번역 저장 미지원 | 원본 그대로 보존 + PDF, DOCX (변환 성공 시) |

DOC/HWP는 OnlyOffice에서 읽을 수 있어도 해당 형식으로 다시 쓰지는 못합니다.
변환 실패 항목과 지원하지 않는 형식은 UI와 API에서 차단합니다. 원본 보존 결과는
바이트 단위로 동일하며, 번역 결과로 표시하지 않습니다. 비-PDF 파일은 `/native` 화면에서
원본 보존 또는 원본 형식 번역을 선택합니다. 파일은 lab의 `native-data/`에 저장됩니다.

번역 시 이미지·서식·관계·페이지/슬라이드 구조를 재생성하지 않고 텍스트 노드를 교체합니다.
번역 길이·글꼴 대체에 따른 줄바꿈/넘침은 발생할 수 있으므로 미리보기에서 검토해야 합니다.
이미지 글자, 차트 데이터, 슬라이드 마스터, 삽입 개체는 원본을 유지하며 번역하지 않습니다.
렌더링 후 페이지 크기·수, 대응하지 못한 문자, 페이지 밖 블록을 보고합니다. 자동 검사는
픽셀 단위 서식 일치나 의미상 완전한 번역을 보증하지 않습니다. HWPX는 실제 문서별 검토가 필요합니다.

PDF 기반 DOCX/PPTX는 텍스트 상자 방식이며 표 선·그림은 배경 이미지입니다.
DOCX 편집 후 PDF가 갱신되지 않으면 PDF/PPTX Export를 차단합니다.
`슬라이드 Export 가능 여부 확인`은 PPTX를 실제 렌더링하고 페이지·텍스트를 검사합니다.
PDF→HWP/HWPX와 문서→PPTX 같은 미구현 변환은 표시하지 않습니다.

기존 `backend/`, `frontend/`를 수정하지 않는 로컬 실험실입니다.
새 경로는 영역별 OCR·번역·조판을 사용합니다. 기존 경로는 실제 프로젝트의 PDF 분석·대조·번역·이미지 처리·DOCX 생성 파이프라인을 사용합니다.

## 실행

프로젝트 루트에서 PowerShell:

```powershell
cd pdf-layout-lab
python -m pip install -r requirements.txt
python -m uvicorn app:app --host 127.0.0.1 --port 8011
```

브라우저에서 http://127.0.0.1:8011 을 엽니다. 기존 개발 서버와 다른 포트를 사용합니다.
의존성이 이미 설치되어 있으면 설치 단계는 생략할 수 있습니다.
MuPDF 접근을 직렬화하므로 **단일 worker**로 실행하세요. 인증 없는 로컬 실험 도구이며 외부 공개 서버 용도가 아닙니다.

## 사용

번역·비교 실행 중에는 문서 분석 → 이미지 글자 읽기 → 번역 → 새 PDF 조판·검증 →
새 DOCX 생성 → 새 DOCX의 OnlyOffice PDF 변환 → 기존 프로젝트 처리 → 기존 PDF 변환 →
결과 저장 단계를 표시합니다. 전체·단계별 경과 시간은 완료 후에도 보고서의 `processing`에 남습니다.
OCR 영역/번역 묶음처럼 실제 처리량을 아는 단계만 진행 막대를 표시하며, OnlyOffice 변환에는
임의의 백분율이나 예상 완료 시간을 표시하지 않습니다. 상태 조회는 PDF 처리 잠금과 분리되어 있습니다.
이 실험은 두 출력 경로를 순차 생성하므로 기존 프로젝트와 처리 시간이 같지 않습니다.

1. 원본 PDF를 업로드합니다 (25MB, 최대 60페이지, 페이지 한 변 최대 2,500pt).
2. 원문·번역 언어를 선택하고 `번역 후 결과 생성·비교`를 누릅니다. 새 경로는 영역별 번역을 사용합니다. 기존 경로는 동일 PDF 해시·원문 언어·대상 언어의 프로젝트 저장 DOCX가 있으면 가장 최근 저장본을 읽기 전용으로 복사합니다. 없으면 기존 전체 파이프라인을 lab 캐시에서 실행합니다. 저장본의 수동 편집·용어집 설정도 결과에 포함될 수 있으며, 두 경로의 번역문은 동일하지 않을 수 있습니다.
3. 새 경로의 기본 PDF는 영역에 직접 조판한 결과를 유지합니다. 이 PDF에서 `layout.docx`를 만들고 OnlyOffice 변환본을 별도 미리보기 파일로 저장하지만, Word의 폰트·간격 변환으로 기본 PDF를 덮어쓰지 않습니다. 원본 / 새 레이아웃 PDF / 기존 프로젝트 DOCX의 PDF 변환본을 비교합니다. DOCX는 줄별 텍스트 상자로 편집할 수 있고 표 선·그림은 배경으로 보존합니다. 사용자가 DOCX 편집기에서 명시적으로 저장·미리보기를 갱신한 경우에는 그 편집본의 PDF를 표시합니다.
4. 영역을 클릭하면 원문·폰트·좌표를 확인할 수 있습니다.
5. 별도의 레이아웃 단독 테스트에서는 `REPLAY`로 원문 재삽입, `FIT`으로 직접 입력한 교체문의 배치를 시험합니다.
6. `새 DOCX 다운로드` 또는 `새 DOCX 편집`을 누릅니다. 편집기는 OnlyOffice를 사용하며 `저장하고 미리보기 갱신`으로 저장 완료를 확인한 뒤 비교 화면을 새로고침합니다. 최초 생성본은 편집 저장 시 `layout.generated.docx`로 보존됩니다. 기존 DOCX는 별도 다운로드할 수 있습니다.

### 확인한 영역 적용

- `여러 영역 선택`에서 확인한 교체문을 체크하고 한 번에 적용할 수 있습니다. 페이지를 이동해도 선택은 유지되며, 선택하지 않은 영역의 작성 중인 교체문은 적용하지 않습니다.
- 한 영역 적용과 여러 영역 적용 모두 번역 API를 호출하지 않습니다. 일반 PDF는 선택한 영역이 있는 페이지만 원본에서 재조판하고 검사하며, 나머지는 이전 결과와 검사 기록을 재사용합니다. 링크·주석·폼·목차가 있으면 구조 보존을 위해 전체 조판·검사 경로를 사용합니다.
- 적용 결과에 성공/원문 유지 개수와 사유를 표시합니다. 이전 실행은 보존하며, 다른 실행에서 변경한 오래된 화면의 요청과 DOCX 수동 편집 이후 요청은 거절합니다.
- 수동 영역 적용 때는 PDF를 먼저 제공합니다. 전체 DOCX를 매번 다시 만드는 시간을 줄이기 위해, 필요할 때 `DOCX 편집·내보내기 준비`로 최신 PDF에 대응하는 편집본을 생성합니다. 이전 DOCX가 최신 결과로 잘못 제공되지 않습니다.

### DOCX 레이아웃 보존 범위

- 새 엔진 구현·편집 API·화면은 `pdf-layout-lab` 안에만 있습니다. 기존 `backend/`, `frontend/` 코드는 수정하지 않으며, 기존 프로젝트 저장 결과는 읽기만 합니다. 새 비교 분석·번역 산출물은 lab의 `data/_cache/.../project-pipeline/`에 저장합니다.
- 텍스트는 줄별로 편집할 수 있습니다. 표 선·이미지·도형은 배경 이미지이며, Word 표 셀이나 개별 도형으로 재구성되지는 않습니다. 긴 수정문은 이웃 영역과 겹칠 수 있으므로 저장 후 미리보기를 확인하세요.
- 회전된 텍스트와 OCR로 읽지 못한 이미지 글자는 배경으로 남을 수 있으며 검토 경고에 표시됩니다. 배경 그림은 144dpi로 보존합니다.
- 자동 픽셀·영역 검증은 직접 조판한 기본 PDF 기준입니다. DOCX에는 폰트 대체와 Word 배치 차이가 발생할 수 있어 별도 미리보기 확인이 필요합니다. 수동 편집 후에는 기존 출력과 번역문이 달라질 수 있습니다.
- 기존 실행의 PDF만 새로고침해도 DOCX가 생기지는 않습니다. `번역 후 두 DOCX 생성`을 다시 실행하면 분석·번역 캐시를 재사용합니다. 레이아웃 단독 테스트도 새 DOCX를 생성하며 편집기의 저장·갱신으로 미리보기를 만들 수 있습니다.

## 번역 비교 설정

`./start.ps1`은 기존 `backend/.venv`가 있으면 이를 사용합니다. 해당 환경에 requirements.txt 의존성이 필요합니다.
`backend/.env`의 API 설정을 읽으며, 별도 설정은 `.env.example`을 참고하여 lab의 `.env`에 넣습니다. 키는 브라우저에 전달하지 않습니다.
번역 비교는 추출 텍스트와 이미지/OCR 보완용 글자 영역을 설정된 API로 전송합니다. 동일 입력·분석 내용·언어·번역 설정은 캐시를 재사용합니다. 영역 구성이 달라지면 번역 캐시도 바뀝니다.
OnlyOffice 서비스와 기존 backend의 변환 설정이 필요합니다. OnlyOffice에서 `LAB_PUBLIC_URL`에 접근할 수 있어야 합니다. 기본값은 `http://host.docker.internal:8011`이며, 환경에 따라 바인딩 주소·방화벽 설정이 필요합니다. 변환 입력은 짧게 유효한 토큰 URL로 제공됩니다.

### Windows에서 기존 PDF 변환 서버 연결

1. Docker Desktop을 설치하고 Linux 컨테이너 엔진을 실행합니다.
2. 프로젝트 루트 PowerShell에서 실행합니다.

```powershell
docker compose -f docker-compose.yml -f pdf-layout-lab/compose.onlyoffice-local.yml up -d onlyoffice
Invoke-RestMethod http://localhost:8080/healthcheck
```

초기 기동 후 `true`가 반환되어야 합니다. 이 로컬 전용 override는 OnlyOffice가 호스트의 DOCX 주소에 접근하도록 사설 IP 접근을 허용합니다.

3. `pdf-layout-lab/.env` 또는 `backend/.env`에서 아래 주소를 확인합니다. `ONLYOFFICE_JWT_SECRET`은 `docker-compose.yml`의 `JWT_SECRET`과 같아야 합니다. 현재 compose 기본 개발 값은 `devsecret_change_me`입니다. API 키 등 기존 설정은 유지하세요.

```dotenv
ONLYOFFICE_DS_INTERNAL_URL=http://localhost:8080
ONLYOFFICE_PUBLIC_URL=http://localhost:8080
LAB_PUBLIC_URL=http://host.docker.internal:8011
```

4. 진행 중인 번역 작업이 끝난 다음 기존 lab 서버를 종료하고 다음 명령으로 재시작합니다. Docker에서 DOCX를 가져올 수 있도록 호스트 인터페이스에서 수신합니다. 로컬 개발 네트워크에서만 사용하세요.

```powershell
./pdf-layout-lab/start.ps1 -ListenHost 0.0.0.0
```

5. 컨테이너에서 lab 연결을 검사합니다.

```powershell
docker exec onlyoffice-ds curl --fail http://host.docker.internal:8011/
```

HTML이 반환되면 문서를 선택하고 `번역 후 두 출력 생성`을 실행합니다. 동일 입력/설정의 번역은 캐시를 사용하고 DOCX→PDF 변환을 재시도합니다. `healthcheck` 실패는 Docker/8080 문제, 컨테이너의 lab 접속 실패는 수신 주소/방화벽 문제, 변환 오류 코드가 나타나면 JWT와 다운로드 주소를 확인합니다.

공식 설치 문서: https://docs.docker.com/desktop/setup/install/windows-install/ · https://helpcenter.onlyoffice.com/docs/installation/docs-community-install-docker.aspx

이 비교는 **새 영역 기반 경로와 기존 프로젝트 전체 파이프라인의 결과 비교**입니다. 비교 보고서의 `project_result`에 저장본/전체 실행 구분과 DOCX 해시를 남깁니다. 이전 문단 변환 결과는 UI에 이전 실험으로 표시합니다. 번역 JSON과 기존 DOCX도 다운로드할 수 있습니다. 새 엔진에서 배치에 실패한 영역은 원문으로 남으므로 검증 결과를 함께 확인하세요.

## 아키텍처

DOCX 편집본은 결과 PDF의 번역문뿐 아니라 저장된 OCR 원문도 사용합니다. PDF에서 `NEEDS_REVIEW` 또는 `UNCHANGED`로 남은 스캔 텍스트는 원문 잉크를 지운 배경 위에 편집 가능한 텍스트 상자로 복원합니다. 검증·보정된 원문을 사용하며 미반영 번역문을 대신 넣지 않습니다. 90° 공정명도 Word 텍스트 방향을 사용해 편집할 수 있습니다. 표 선과 그림은 배경이므로 Word 표 셀 편집은 아닙니다.

복원 시 OCR 오독과 글꼴·행 위치 차이는 원본과 대조해야 합니다. 인식되지 않은 `[OCR]`, 보호된 체크 표시·워터마크, 이미 배치된 이웃 텍스트와 충돌하는 곳은 배경으로 남기며 `docx_output.original_regions`에 편집 여부와 사유를 기록합니다. 비교 화면의 영역별 상태와 DOCX 편집기에서 이를 안내합니다. 원문 복원만으로 기본 PDF를 변경하지 않으며, 사용자가 DOCX를 저장하고 미리보기를 갱신할 때 편집 결과가 PDF에 반영됩니다.

기존 생성본은 `POST /api/documents/{id}/editable-docx?run={latest_run}`으로 번역·OCR 재호출 없이 새 DOCX 실행을 만들 수 있습니다. 이전 실행과 기본 PDF 바이트를 보존하며, 이미 수동 편집한 DOCX와 오래된 실행을 대상으로 한 요청은 거부합니다.

```
원본 PDF → inspect.py (업로드 미리보기)
         → enhanced.py + ocr_review.py (번역 비교: 셀·문단·이미지 글자 분석)
         → typesetter.py (REPLAY / FIT 사전 조판)
         → service.py (원문 일괄 제거 → 삽입 → 별도 PDF 저장)
         → validate.py (다시 열기 + 자동 검사)
```

레이아웃 모델, 교체 요청, 출력 보고서는 영역 ID로 연결됩니다.
`REPLAY`는 원본 폰트 임베딩 데이터 또는 표준 14폰트와 문자별 origin을 사용합니다.
원본 폰트의 글리프 매핑을 재사용할 수 없으면 임의 대체하지 않고 해당 영역을 보존합니다.
`FIT`는 MuPDF HTML 조판의 sans-serif/CJK 대체 폰트를 사용합니다. 새 분석 모델에서는 혼합 서식을 대표 서식으로 통일하며, 원본 폰트/부분 강조의 동일성은 보장하지 않습니다.
사전 조판이 실패하면 해당 영역은 원문 그대로 남고 `NEEDS_REVIEW`가 됩니다.

## 실험 범위와 해석

- 번역 비교는 벡터 표 선과 이미지 표의 격자를 분석해 셀을 구성합니다. 바깥 프레임을 셀로 오인하지 않도록 내부 셀과 구분합니다. 테두리 없는 표의 완전한 의미 추론은 지원하지 않습니다.
- 이미지 글자의 위치는 RapidOCR 검출기로 찾고, 영역별 이미지를 API로 읽습니다. Tesseract는 도형 글자의 위치·초기 원문 보완에 사용합니다. 회전/세로 텍스트와 특수 그래픽 상태의 완전한 재현은 지원하지 않습니다.
- 겹치는 블록, 링크·주석·폼과 겹치는 영역, 기존 삭제 주석 페이지는 수정하지 않습니다.
- 폰트·기준선·텍스트 분리 특성 때문에 REPLAY도 픽셀 동일성이 보장되지는 않습니다.
- 자동 검사는 페이지 기하, 영역별 추출 텍스트, 72dpi에서 수정 영역 밖 픽셀 변화(색 차이 허용치 12, 마스크 여유 2pt), 링크·주석 개수를 확인합니다.
- 자동 검사 통과는 전체 시각 동일성, 태그/접근성, 검색 순서, 폼·전자서명 유효성 보증이 아닙니다. 결과는 시각적으로도 확인하세요.
- 교체 글자 모양은 달라지므로 전체 페이지 픽셀 차이를 번역 품질 점수로 쓰지 않습니다.
- 스캔/빈 페이지, 미처리 영역 또는 검사 오류가 있으면 문서 결과를 검토 필요로 표시합니다.
- 기존 출력은 페이지 수가 달라질 수 있습니다. 의미 기반 페이지 매칭은 하지 않습니다.
- 각 실행은 항상 원본에서 시작합니다. `data/<uuid>/runs/<uuid>/`에 출력 PDF와 보고서를 보관하므로 이전 실행을 덮어쓰지 않습니다.
- FIT 텍스트 수정은 브라우저 메모리에 있다가 재생성 시 보고서에 저장됩니다. 재생성 전 새로고침하면 사라집니다.
- 원문 PDF·분석 정보·실행 결과는 `data/`에 저장됩니다. 번역 비교에서는 텍스트와 OCR 보완용 이미지 영역이 설정된 API로, 기존 출력 생성에서는 DOCX가 설정된 OnlyOffice로 전달됩니다. 레이아웃 단독 테스트는 번역 API를 사용하지 않습니다.

## 테스트

### 미반영 사유에 따른 자동 배치 조정

번역문 배치 전 `placement_quality.py`가 같은 열·실제 표 셀의 빈 공간을 먼저 확보합니다. 넓은 본문이 없는 표 중심 페이지에서는 표 바깥 경계도 열의 오른쪽 여백 판단에 활용합니다. 이웃 글자, 다른 열, 셀 경계, 선·그림·주석은 넘지 않으며 원본 좌표와 삭제 마스크는 확장하지 않습니다. 사용자 지정 박스와 이미지 내부 영역은 기존 제약을 유지합니다.

조판 v4는 원래 크기·굵기로 먼저 시도하며, 짧은 굵은 제목은 한 줄을 우선합니다. 제목·본문을 크기만으로 함께 축소하지 않습니다. 원래 크기로 들어가지 않으면 간격 조정 후보까지 비교한 뒤 허용된 크기 범위에서 배치합니다. 이미 반영된 영역도 새 출력 생성 시 재평가합니다. 원문 대비 제목 90%, 본문 85% 미만으로 축소되면 반영 여부와 별도로 가독성 검토를 표시합니다. 직접 입력한 엔터는 유지합니다. 영역 패널에서 원문/결과 글자 크기와 빈 공간 활용 여부를 볼 수 있습니다. 이 단계는 번역 API를 호출하지 않으며, 측정한 표·도형 경계는 후속 부분 적용에 재사용합니다.

`placement_recovery.py`는 조판에서 공간 부족이 발생하면 내부 여백 → 행 간격 → 긴 단어 줄바꿈 → 같은 열의 빈 공간 또는 감지된 표 셀 내부 → 표 칸의 간격 조정 순서로 제한된 재시도를 수행합니다. 번역문·원본 좌표·삭제 마스크·사용자가 입력한 엔터는 변경하지 않습니다. 각 후보는 임시 PDF에서 텍스트 누락, 경계 이탈과 이웃 영역 겹침을 확인한 뒤 채택합니다. 사용자 지정 박스, 그림의 배치 박스, 표 셀 밖으로는 확장하지 않습니다. 최소 글자 크기 안에서 해결되지 않으면 원문을 유지합니다.

보고서의 `adjustment`에 최초 실패 이유, 시도별 결과, 변경 전후 박스가 기록되며 영역 패널에도 표시됩니다. 번역 응답 누락·보호 영역·판독 불가는 공간 조정으로 강제 적용하지 않습니다. 기존 실행은 남겨 두며 새 PDF 생성 또는 선택 영역 적용부터 이 단계가 실행됩니다.

분석 v16 및 `native_refinement.py`는 같은 표 셀의 번호 항목과 뒤따르는 줄을 묶고, 확인된 특수 글꼴의 글머리표를 표준 문자로 복원합니다. 표 본문의 물리적 줄바꿈은 번역 단위에서 연결하며, 별도 목록 시작과 다른 셀은 유지합니다. 이미지 배경색은 글자 밀도에 덜 민감하게 측정해 같은 패널의 연속 줄을 연결합니다.

번역 프로토콜 v2는 결과 ID와 대응 원문을 함께 검사합니다. 기존 v1 캐시의 잘못된 연결을 재사용하지 않도록 캐시를 분리하며, 새 캐시는 동일한 내용에 재사용됩니다. 독립 요청은 최대 3개까지 동시에 실행합니다. 취소나 오류 시 대기 중인 요청을 취소하고 이미 완료한 번역은 보관합니다.

### 번역 단위 분리 1차 구현

번역 비교는 OCR 원문 보완 후 `translation_units.ensure`에서 세 모델을 구성합니다.

- `source_regions`: 추출 당시의 줄·영역 원문, 좌표, 글자별 서식, 삭제 마스크. 병합·분리·박스 조절로 변경하지 않습니다.
- `translation_units`: 원본 영역 ID 목록, 번역 원문, 참고 문맥, 번역 결과·상태. 자동 문단 묶기 규칙은 기존 분석 v15를 사용합니다.
- `placement_spaces`: 번역 단위 ID, 배치 박스, PDF 반영 상태·사유. 1차에서는 같은 페이지의 연속된 배치 공간 하나를 지원합니다.

`pages[].regions`는 기존 조판·DOCX 엔진을 위한 호환 뷰이며, 렌더링 전에 번역 단위 원문과 배치 공간으로 갱신합니다. 기존 실행은 읽기 시 호환 모델로 표시하고 저장 파일을 덮어쓰지 않습니다. 새 분석·OCR은 기존 캐시를 재사용할 수 있지만, 참고 문맥과 ID 응답 검증이 추가된 번역 캐시는 별도로 저장하므로 새 규격의 첫 번역은 다시 호출될 수 있습니다.

번역 API 입력은 `segments[{id,text,kind,flow,context_before,context_after}]`, 출력은 `translations[{id,text}]`입니다. 좌표는 보내지 않고 참고 문맥은 번역 대상에서 제외합니다. 응답 순서는 달라도 되지만 ID 누락·중복·알 수 없는 ID·빈 문장은 검증하며, 유효한 결과를 먼저 저장하고 실패한 항목만 제한적으로 재시도합니다. 목록 번호·체크 기호·직접 입력한 줄바꿈은 기존 경로대로 보존합니다. 캐시는 언어·모델·용어집·원문·참고 문맥·프로토콜을 기준으로 하며 위치·박스·ID는 키에서 제외합니다.

비교 화면의 **번역 묶음 · 원본 영역 연결**에서 원본 영역과 배치 공간 보기를 전환할 수 있습니다. 원본 영역을 클릭하면 같은 묶음의 영역이 함께 강조됩니다. 여러 묶음을 선택해 합치거나 원본 줄 경계를 선택해 나눌 수 있습니다. 묶음 변경은 API를 호출하지 않으며 그 단위만 번역 대기로 돌리고 원문 PDF를 복원합니다. **이 영역만 다시 번역·적용** 또는 교체문 입력으로 다시 반영합니다. 표 셀·이미지·다른 열·떨어진 본문은 이 자동 연속 문단 편집 대상이 아닙니다. 기존 영역 편집·다중 적용·DOCX 편집 기능은 유지합니다.

## 표·이미지 처리 (새 번역 비교)

- `enhanced.py`: 원본 글자 + 도형 글자 OCR + 이미지 문자 검출 → 셀/문단 구성.
- `ocr_review.py`: 이미지 글자는 비율을 유지한 여백을 붙여 읽고, 도형과 원래 텍스트가 섞인 영역은 원문을 보완합니다. 문서에 인쇄된 지시는 데이터로 취급합니다. 작은 이미지의 숫자·고유명사·서명은 오독할 수 있어 OCR 결과는 검토 대상으로 표시합니다.
- 같은 배경·색상·크기의 인접 이미지 줄은 문단으로 묶습니다. 이웃 영역의 여백은 중간 지점에서 나눠 번역문이 서로 겹치지 않도록 합니다. 경계가 없는 표 열을 페이지 끝까지 임의 확장하지 않습니다.
- 이미지 OCR은 페이지당 450dpi 이미지를 한 번 만들고 셀/문단별로 잘라 최대 6개 영역씩 요청합니다(동시 요청 4개). 전체 문서 이미지를 먼저 메모리에 모으지 않고 페이지 단위로 처리합니다. 도형/네이티브 혼합 원문 보완은 별도 220dpi 페이지 이미지 한 장을 사용합니다.
- 응답 ID 누락·중복·잘림은 해당 영역을 개별 재시도합니다. OCR 이미지 준비와 인식 완료 진행률을 별도로 표시합니다. 요청 횟수 감소가 같은 비율의 시간 단축을 보장하지는 않습니다.
- 동일 PDF 재업로드는 파일 SHA-256 기준 `data/_cache/<hash>/`의 분석·OCR·번역 캐시를 공유합니다. OCR은 모델·프롬프트·좌표·방식 버전을 검사하며, 새 방식의 캐시가 있으면 페이지 이미지도 만들지 않습니다. 이전 방식의 OCR 캐시는 보존하지만 방식이 바뀐 최초 실행에서는 새로 인식할 수 있습니다.
- 원본 텍스트는 삭제하고, 이미지/도형 글자는 해당 영역의 배경색으로 지운 뒤 번역문을 삽입합니다. 표 선을 별도 보호합니다. 페이지 전체를 이미지로 바꾸지는 않습니다.
- 복잡한 사진 배경은 균일색 복원으로 안전하게 처리할 수 없어 원문 유지/검토 필요로 표시합니다. 인식 불가·공간 부족도 조용히 성공 처리하지 않습니다.
- 기본 최소 크기는 3pt, 최소 비율은 40%입니다. 작은 도표를 위한 하한이며, 5pt 미만은 검증 경고를 표시합니다. 가독성이 중요하면 UI에서 하한을 높이세요. 작은 원본 영역에 긴 번역을 넣으면서 크기까지 동일하게 보존하는 것은 불가능할 수 있습니다.
- 번역문과 같은 고유명사/기호는 원본을 유지하며, 번역 배치 수와 구분합니다.

## 목록·체크란과 직접 입력 줄바꿈

분석 v11부터 반복된 목록 번호와 열 사이 여백을 이용해 큰 표 셀의 목록을 행·열별 영역으로 분리합니다. 항목의 원래 시작 위치를 유지해 들여쓰기를 보존하고, 같은 행의 체크란이 본문 번역문에 합쳐지지 않게 합니다. 스캔 체크란에서 `표시-설명-표시-설명`을 확실히 분리할 수 있으면 표시의 원본 픽셀은 유지하고 설명만 번역합니다. 분리가 불확실한 칸은 선택 상태를 추측하지 않고 원문과 검토 사유를 남깁니다. 표 밖의 모든 목록이나 모든 체크박스 모양을 완전하게 인식하는 것은 아닙니다.

번역 어댑터는 줄 경계·들여쓰기·목록 번호·체크 기호를 구조로 보관하고 텍스트만 번역합니다. FIT에서는 교체 텍스트에 직접 입력한 엔터, 빈 줄, 선행 공백을 PDF에 반영합니다. 한 줄 안에서만 길이에 따라 자동 줄바꿈하며, 공간이 부족하면 조용히 줄을 합치지 않고 배치 실패로 표시합니다. 기존 분석 결과의 구조 분할은 **번역 후 결과 생성·비교**를 다시 실행해야 적용됩니다. 직접 입력한 줄바꿈 보존은 기존 영역의 재생성에도 적용됩니다.

## 원문 여백과 반복 머리말

분석 v12부터 일반 본문은 PDF 내부 블록 대신 문단·목록 경계로 다시 묶습니다. 자동 번역의 시각적 줄바꿈은 문단 안에서 재배치하고, 같은 페이지의 동일한 본문 크기는 함께 맞춥니다. 제목·본문의 굵기와 문장 앞부분의 강조를 보존하며, 폰트 플래그가 누락된 경우에는 같은 글자의 원본 픽셀 밀도를 비교해 충분한 근거가 있는 굵기만 복원합니다. 사용자가 영역 적용 또는 전체 재생성에서 직접 수정한 텍스트의 엔터는 이 자동 합침에서 제외합니다.

삽입된 도식의 바깥 테두리는 하나의 표 셀로 취급하지 않습니다. 이미지 라벨과 네이티브 설명을 분리하고, 라벨은 이웃 글자·그림·연결선을 넘지 않는 빈 공간만 사용합니다. 이전 분석에서 도식 전체가 합쳐진 경우에는 좌표를 추측해 지우지 않고 재분석 안내와 원문을 남깁니다. 해당 구조 수정은 **번역 후 결과 생성·비교**를 다시 실행해야 적용됩니다. 긴 이미지 설명의 축소와 작은 글자 경고는 여전히 발생할 수 있습니다.

FIT의 **원문 여백·행 간격·정렬 보존**은 저장된 OCR/텍스트 좌표로 문단의 시작 위치, 셀 내부 여백, 행 간격을 복원합니다. 원료명과 수량 사이의 점선은 양쪽 텍스트를 별도 정렬한 뒤 다시 그립니다. 원문과 번역의 줄 구조를 대응할 수 있는 경우에만 행별 위치를 고정하며, 사용자가 엔터·빈 줄을 추가한 경우 입력한 줄 구조를 우선합니다. 너무 좁은 칸은 셀 안에서 여백을 줄이고 그 사실을 영역 반영 상태에 표시합니다.

세 페이지 이상에서 원문과 위치가 일치하는 머리말은 합쳐진 OCR 영역 안에서도 회사명·문서 제목을 나눠 배치하고 공통 글자 크기·정렬을 적용합니다. **반복 머리말의 번역 통일**을 켜면 이미 번역된 표현 중 가장 많이 쓰인 표현으로 맞춥니다. OCR 원문이 다르거나 사용자가 직접 적용한 영역은 번역 통일에서 제외합니다. 고유명사의 번역 정확성을 새로 판단하는 기능은 아닙니다.

기존 결과에서 **교체 텍스트로 재생성**하면 OCR·번역 API 호출 없이 적용됩니다. 이전 실행과 원본 분석/번역 캐시는 유지하며, 새 실행의 layout/report에 배치 근거와 통일된 번역을 저장합니다. 스캔 기울기·부정확한 OCR 영역·긴 번역 때문에 모든 여백을 정확히 재현할 수는 없습니다.

배치 v5는 정렬된 짧은 표 셀 아래의 좁고 긴 세로 한글 항목명을 구분해 영어 항목명만 90° 회전합니다. 번호와 `I·II`는 가로로 남깁니다. 번호·공정명이 별도 OCR 영역이면 이웃 영역 사이의 빈 공간만 활용하며, 안전한 공간이 부족하면 검토 대상으로 표시합니다. 공정명은 8pt 미만으로 줄이지 않습니다. 서명이나 일반 본문에는 이 규칙을 적용하지 않습니다.

점선 항목은 실제 출력 폰트로 수량의 너비를 측정해 수량 칸을 넓히고 점선을 줄입니다. 긴 항목명은 다음 행을 침범하지 않는 범위에서 줄바꿈하고, 수량은 항목명의 마지막 줄에 맞춥니다. 한 행 때문에 묶음 전체를 축소하지 않으며, 원래부터 작은 글자를 제외하면 8pt 또는 사용자 최소 크기보다 작게 줄이는 대신 검토 사유를 남깁니다. `㎥`·`℃`는 같은 의미의 `m³`·`°C`로 표시해 출력 폰트의 문자 매핑 문제를 피합니다. 기본 PDF의 회전 글자는 검색할 수 있지만, 현재 추가 DOCX Export에서는 배경 이미지로 보존됩니다.

## 워터마크와 영역 반영 상태

회전·투명 네이티브 텍스트를 본문 셀과 분리합니다. 검정 OCR 본문과 겹친 색상 워터마크는 글자별 좌표·색상을 사용해 보존하면서 본문을 교체합니다. 흑백 워터마크, 본문과 색상이 비슷한 경우, 회전된 본문 등 안전하게 구분할 수 없는 겹침은 검토 대상으로 남깁니다. 이미지에 합쳐진 워터마크를 일반적으로 제거·분리하는 기능은 아닙니다. 분석 버전이 변경되어 첫 실행에서는 OCR 재분석이 필요할 수 있습니다.

영역 선택 시 PDF 반영 여부, 원문 유지 사유, 미저장 교체문을 표시합니다. 새 보고서는 최종 PDF의 대응 페이지에 번역문이 있는지도 확인합니다. 이 텍스트 검사는 픽셀 배치·겹침의 정확성 보장이 아니며, DOCX 수동 편집 후에는 최초 영역 보고서 대신 미리보기를 검토해야 합니다.

FIT 모드의 **확인한 교체문을 이 영역에 적용**은 선택 영역의 번역문만 저장 결과에 합쳐 PDF를 재생성합니다. 다른 영역의 미저장 초안은 적용하지 않으며 번역 API를 호출하지 않습니다. 이전 실행 파일은 보존합니다. OCR 인식 경고와 실제 글자가 충돌하지 않는 배치 박스 겹침은 사용자 확인으로 재정의하며, 적용 기록과 기존 사유를 보고서에 남깁니다. 실제 이웃 글자·스캔 마스크·번역문 간의 충돌은 수동 확인으로 우회할 수 없습니다. 페이지 경계·공간 부족·워터마크·주석 보호와 출력 검증은 유지됩니다. 회전 워터마크가 섞인 이전 버전 영역은 번역 비교를 다시 실행해 분리해야 합니다. DOCX 수동 편집 결과는 덮어쓰지 않도록 해당 버튼을 비활성화합니다.

영역 합치기·박스 조절: FIT 결과에서 같은 페이지의 영역을 선택해 병합을 준비하고 원문 순서와 X/Y/폭/높이(pt)를 확인합니다. 박스 편집 모드에서는 원본 PDF 위에서 이동하고 오른쪽 아래 손잡이로 크기를 조절합니다. 저장 전에는 초안이며, 저장 시 원문 삭제 마스크는 유지하고 번역문 배치 공간만 바꿉니다. 다른 원문을 침범하거나 보호 영역·체크 표시·위치 미확정 도식을 포함하는 편집은 거절합니다. 서로 다른 페이지 및 이미지/일반 텍스트 혼합 병합은 지원하지 않습니다.

‘이 영역만 다시 번역·적용’은 선택 또는 병합한 원문만 API로 보내며 강제 재번역합니다. 일반 ‘박스·원문 저장하고 교체문 적용’은 API를 호출하지 않습니다. 병합한 원문은 전체 문맥을 한 번에 번역합니다. 원문의 물리적 줄바꿈은 배치에 맞게 재조판하고, 사용자가 교체문에 직접 넣은 엔터는 보존합니다. 변경된 페이지만 렌더링하고 DOCX 생성은 필요할 때 수행합니다. 기존 실행은 남으며 전체 번역·비교를 다시 실행하면 자동 분석으로 새 실행을 만듭니다.

분석 v15는 같은 문단의 네이티브 텍스트를 줄 간격·들여쓰기·글자 크기·영역 경계로 연결합니다. 검정과 짙은 회색의 미세한 색상 차이는 문단을 자르지 않으며, 새 목록 항목·제목·구분선·그림·다른 표 셀은 경계로 유지합니다. 여러 열은 페이지 전체의 단순 위아래 순서가 아닌 같은 열의 이전 줄과 연결합니다. 좁은 열 간격은 주변 줄에서도 반복되는지 확인하고, 같은 크기의 주변 본문이 그 간격을 가로지르면 문장 내부 띄어쓰기로 유지합니다. 원문은 `source_fragments`와 `spans`에 각 줄의 좌표·폰트·색상·강조를 보관하고, `logical_paragraph`가 표시된 단위 전체를 번역 API에 보냅니다. 번역 API에 물리적 줄바꿈이 단어를 자를 수 있다는 문맥을 전달하며, 반환된 문단은 하나의 배치 공간에서 재조판합니다. 표 셀 안의 연속 문장은 셀 내부에서만 처리하고 목록·체크박스의 구조는 따로 보존합니다. 이전 줄별 번역 캐시는 새 문단 번역에 사용하지 않습니다. 기존 결과에는 **번역 후 결과 생성·비교**를 다시 실행해야 적용됩니다.

문장 캐시 키는 언어·모델·용어집·번역 코드 기준이며 좌표·영역 ID·분석 버전 변경에는 영향을 받지 않습니다. 새 문장 캐시가 쌓인 후부터 부분 변경 재번역을 줄입니다. Lab OpenAI 요청은 60초 timeout, SDK 재시도 1회이며 형식 복구는 한 묶음당 최대 6회 추가 호출합니다. 기존 프로젝트 번역기의 중첩 분할 재시도를 Lab에서는 사용하지 않습니다. 진행 화면에 캐시 적중 문장 수, 응답 오류 복구와 API 호출 시간 통계를 표시합니다.
