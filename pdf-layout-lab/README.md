# PDF Layout Lab

## Smart Export

입력: PDF, DOC, DOCX, HWP, HWPX, PPTX (25MB 이하). 기본 출력은 원본 형식입니다.

| 입력 | 원본 형식 번역 | 추가 Export |
|---|---|---|
| PDF | 기존 영역 번역 경로 | DOCX; 동일 크기 가로형 페이지는 PPTX 생성·렌더링 검증 후 제공 |
| DOCX | 원본 패키지 텍스트 교체 | PDF |
| PPTX | 원본 슬라이드 텍스트 교체 | PDF |
| HWPX | 원본 섹션 텍스트 교체, 줄 위치 캐시 재계산 | PDF, DOCX (변환 성공 시) |
| DOC, HWP | 현재 엔진은 원본 형식 번역 저장 미지원 | 원본 그대로 보존 + PDF, DOCX (변환 성공 시) |

DOC/HWP는 OnlyOffice에서 읽을 수 있어도 해당 형식으로 다시 쓰지는 못합니다.
변환 실패 항목과 지원하지 않는 형식은 UI와 API에서 차단합니다. 원본 보존 결과는
바이트 단위로 동일하며, 번역 결과로 표시하지 않습니다. 비-PDF 파일은 `/native` 화면에서
원본 보존 또는 원본 형식 번역을 선택합니다. 파일은 lab의 `native-data/`에 저장됩니다.

번역 시 이미지·서식·관계·페이지/슬라이드 구조를 재생성하지 않고 텍스트 노드를 교체합니다.
번역 길이·글꼴 대체에 따른 줄바꿈/넘침은 발생할 수 있으므로 미리보기에서 검토해야 합니다.
이미지 글자, 차트 데이터, 슬라이드 마스터, 삽입 개체는 원본을 유지하며 번역하지 않습니다.
렌더링 후 페이지 크기·수, 대응하지 못한 문자, 페이지 밖 블록을 보고합니다. 자동 검사는
픽셀 단위 서식 일치나 의미상 완전한 번역을 보증하지 않습니다. HWPX는 실제 문서별 검토가 필요합니다.

PDF 기반 DOCX/PPTX는 텍스트 상자 방식이며 표 선·그림은 배경 이미지입니다.
DOCX 편집 후 PDF가 갱신되지 않으면 PDF/PPTX Export를 차단합니다.
`슬라이드 Export 가능 여부 확인`은 PPTX를 실제 렌더링하고 페이지·텍스트를 검사합니다.
PDF→HWP/HWPX와 문서→PPTX 같은 미구현 변환은 표시하지 않습니다.

기존 `backend/`, `frontend/`를 수정하지 않는 로컬 실험실입니다.
번역 비교에서는 기존 backend 번역 로직과 DOCX 렌더러를 재사용합니다.

## 실행

프로젝트 루트에서 PowerShell:

```powershell
cd pdf-layout-lab
python -m pip install -r requirements.txt
python -m uvicorn app:app --host 127.0.0.1 --port 8011
```

브라우저에서 http://127.0.0.1:8011 을 엽니다. 기존 개발 서버와 다른 포트를 사용합니다.
의존성이 이미 설치되어 있으면 설치 단계는 생략할 수 있습니다.
MuPDF 접근을 직렬화하므로 **단일 worker**로 실행하세요. 인증 없는 로컬 실험 도구이며 외부 공개 서버 용도가 아닙니다.

## 사용

1. 원본 PDF를 업로드합니다 (25MB, 최대 60페이지, 페이지 한 변 최대 2,500pt).
2. 원문·번역 언어를 선택하고 `번역 후 두 DOCX 생성`을 누릅니다. 기존 API 번역 로직으로 번역한 결과를 영역 ID로 저장하고, 동일한 번역문을 새 레이아웃 경로와 기존 DOCX 렌더러에 전달합니다.
3. 새 경로는 PDF 영역에 번역문을 배치한 중간 PDF에서 `layout.docx`를 생성합니다. 원본 페이지 크기·표 선·그림은 배경으로 보존하고 텍스트는 편집 가능한 Word 텍스트 상자로 배치합니다. 기존 경로의 `comparison.docx`와 새 DOCX를 각각 OnlyOffice에서 PDF로 변환하여 원본 / 새 DOCX / 기존 DOCX 미리보기를 비교합니다. 문서 서버가 없으면 DOCX 다운로드는 가능하며 화면에 중간 PDF임을 표시합니다.
4. 영역을 클릭하면 원문·폰트·좌표를 확인할 수 있습니다.
5. 별도의 레이아웃 단독 테스트에서는 `REPLAY`로 원문 재삽입, `FIT`으로 직접 입력한 교체문의 배치를 시험합니다.
6. `새 DOCX 다운로드` 또는 `새 DOCX 편집`을 누릅니다. 편집기는 OnlyOffice를 사용하며 `저장하고 미리보기 갱신`으로 저장 완료를 확인한 뒤 비교 화면을 새로고침합니다. 최초 생성본은 편집 저장 시 `layout.generated.docx`로 보존됩니다. 기존 DOCX는 별도 다운로드할 수 있습니다.

### DOCX 레이아웃 보존 범위

- 새 엔진 구현·편집 API·화면은 `pdf-layout-lab` 안에만 있습니다. 기존 `backend/`, `frontend/`는 비교용으로 읽기만 합니다.
- 텍스트는 줄별로 편집할 수 있습니다. 표 선·이미지·도형은 배경 이미지이며, Word 표 셀이나 개별 도형으로 재구성되지는 않습니다. 긴 수정문은 이웃 영역과 겹칠 수 있으므로 저장 후 미리보기를 확인하세요.
- 회전된 텍스트와 OCR로 읽지 못한 이미지 글자는 배경으로 남을 수 있으며 검토 경고에 표시됩니다. 배경 그림은 144dpi로 보존합니다.
- 자동 픽셀·영역 검증은 중간 PDF 기준입니다. DOCX에는 폰트 대체와 Word 배치 차이가 발생할 수 있어 최종 미리보기 확인이 필요합니다. 수동 편집 후에는 기존 출력과 번역문이 달라질 수 있습니다.
- 기존 실행의 PDF만 새로고침해도 DOCX가 생기지는 않습니다. `번역 후 두 DOCX 생성`을 다시 실행하면 분석·번역 캐시를 재사용합니다. 레이아웃 단독 테스트도 새 DOCX를 생성하며 편집기의 저장·갱신으로 미리보기를 만들 수 있습니다.

## 번역 비교 설정

`./start.ps1`은 기존 `backend/.venv`가 있으면 이를 사용합니다. 해당 환경에 requirements.txt 의존성이 필요합니다.
`backend/.env`의 API 설정을 읽으며, 별도 설정은 `.env.example`을 참고하여 lab의 `.env`에 넣습니다. 키는 브라우저에 전달하지 않습니다.
번역 비교는 추출 텍스트와 이미지/OCR 보완용 글자 영역을 설정된 API로 전송합니다. 동일 입력·분석 내용·언어·번역 설정은 캐시를 재사용합니다. 영역 구성이 달라지면 번역 캐시도 바뀝니다.
OnlyOffice 서비스와 기존 backend의 변환 설정이 필요합니다. OnlyOffice에서 `LAB_PUBLIC_URL`에 접근할 수 있어야 합니다. 기본값은 `http://host.docker.internal:8011`이며, 환경에 따라 바인딩 주소·방화벽 설정이 필요합니다. 변환 입력은 짧게 유효한 토큰 URL로 제공됩니다.

### Windows에서 기존 PDF 변환 서버 연결

1. Docker Desktop을 설치하고 Linux 컨테이너 엔진을 실행합니다.
2. 프로젝트 루트 PowerShell에서 실행합니다.

```powershell
docker compose -f docker-compose.yml -f pdf-layout-lab/compose.onlyoffice-local.yml up -d onlyoffice
Invoke-RestMethod http://localhost:8080/healthcheck
```

초기 기동 후 `true`가 반환되어야 합니다. 이 로컬 전용 override는 OnlyOffice가 호스트의 DOCX 주소에 접근하도록 사설 IP 접근을 허용합니다.

3. `pdf-layout-lab/.env` 또는 `backend/.env`에서 아래 주소를 확인합니다. `ONLYOFFICE_JWT_SECRET`은 `docker-compose.yml`의 `JWT_SECRET`과 같아야 합니다. 현재 compose 기본 개발 값은 `devsecret_change_me`입니다. API 키 등 기존 설정은 유지하세요.

```dotenv
ONLYOFFICE_DS_INTERNAL_URL=http://localhost:8080
ONLYOFFICE_PUBLIC_URL=http://localhost:8080
LAB_PUBLIC_URL=http://host.docker.internal:8011
```

4. 진행 중인 번역 작업이 끝난 다음 기존 lab 서버를 종료하고 다음 명령으로 재시작합니다. Docker에서 DOCX를 가져올 수 있도록 호스트 인터페이스에서 수신합니다. 로컬 개발 네트워크에서만 사용하세요.

```powershell
./pdf-layout-lab/start.ps1 -ListenHost 0.0.0.0
```

5. 컨테이너에서 lab 연결을 검사합니다.

```powershell
docker exec onlyoffice-ds curl --fail http://host.docker.internal:8011/
```

HTML이 반환되면 문서를 선택하고 `번역 후 두 출력 생성`을 실행합니다. 동일 입력/설정의 번역은 캐시를 사용하고 DOCX→PDF 변환을 재시도합니다. `healthcheck` 실패는 Docker/8080 문제, 컨테이너의 lab 접속 실패는 수신 주소/방화벽 문제, 변환 오류 코드가 나타나면 JWT와 다운로드 주소를 확인합니다.

공식 설치 문서: https://docs.docker.com/desktop/setup/install/windows-install/ · https://helpcenter.onlyoffice.com/docs/installation/docs-community-install-docker.aspx

이 비교는 **공통 텍스트 블록과 동일 번역문을 두 렌더러에 넣는 실험**입니다. 기존 운영 파이프라인의 이미지·표 구조 분석 전체를 실행하는 비교는 아닙니다. 번역 JSON과 기존 DOCX도 다운로드할 수 있습니다. 새 엔진에서 배치에 실패한 영역은 원문으로 남으므로 검증 결과를 함께 확인하세요.

## 아키텍처

```
원본 PDF → inspect.py (업로드 미리보기)
         → enhanced.py + ocr_review.py (번역 비교: 셀·문단·이미지 글자 분석)
         → typesetter.py (REPLAY / FIT 사전 조판)
         → service.py (원문 일괄 제거 → 삽입 → 별도 PDF 저장)
         → validate.py (다시 열기 + 자동 검사)
```

레이아웃 모델, 교체 요청, 출력 보고서는 영역 ID로 연결됩니다.
`REPLAY`는 원본 폰트 임베딩 데이터 또는 표준 14폰트와 문자별 origin을 사용합니다.
원본 폰트의 글리프 매핑을 재사용할 수 없으면 임의 대체하지 않고 해당 영역을 보존합니다.
`FIT`는 MuPDF HTML 조판의 sans-serif/CJK 대체 폰트를 사용합니다. 새 분석 모델에서는 혼합 서식을 대표 서식으로 통일하며, 원본 폰트/부분 강조의 동일성은 보장하지 않습니다.
사전 조판이 실패하면 해당 영역은 원문 그대로 남고 `NEEDS_REVIEW`가 됩니다.

## 실험 범위와 해석

- 번역 비교는 벡터 표 선과 이미지 표의 격자를 분석해 셀을 구성합니다. 바깥 프레임을 셀로 오인하지 않도록 내부 셀과 구분합니다. 테두리 없는 표의 완전한 의미 추론은 지원하지 않습니다.
- 이미지 글자의 위치는 RapidOCR 검출기로 찾고, 영역별 이미지를 API로 읽습니다. Tesseract는 도형 글자의 위치·초기 원문 보완에 사용합니다. 회전/세로 텍스트와 특수 그래픽 상태의 완전한 재현은 지원하지 않습니다.
- 겹치는 블록, 링크·주석·폼과 겹치는 영역, 기존 삭제 주석 페이지는 수정하지 않습니다.
- 폰트·기준선·텍스트 분리 특성 때문에 REPLAY도 픽셀 동일성이 보장되지는 않습니다.
- 자동 검사는 페이지 기하, 영역별 추출 텍스트, 72dpi에서 수정 영역 밖 픽셀 변화(색 차이 허용치 12, 마스크 여유 2pt), 링크·주석 개수를 확인합니다.
- 자동 검사 통과는 전체 시각 동일성, 태그/접근성, 검색 순서, 폼·전자서명 유효성 보증이 아닙니다. 결과는 시각적으로도 확인하세요.
- 교체 글자 모양은 달라지므로 전체 페이지 픽셀 차이를 번역 품질 점수로 쓰지 않습니다.
- 스캔/빈 페이지, 미처리 영역 또는 검사 오류가 있으면 문서 결과를 검토 필요로 표시합니다.
- 기존 출력은 페이지 수가 달라질 수 있습니다. 의미 기반 페이지 매칭은 하지 않습니다.
- 각 실행은 항상 원본에서 시작합니다. `data/<uuid>/runs/<uuid>/`에 출력 PDF와 보고서를 보관하므로 이전 실행을 덮어쓰지 않습니다.
- FIT 텍스트 수정은 브라우저 메모리에 있다가 재생성 시 보고서에 저장됩니다. 재생성 전 새로고침하면 사라집니다.
- 원문 PDF·분석 정보·실행 결과는 `data/`에 저장됩니다. 번역 비교에서는 텍스트와 OCR 보완용 이미지 영역이 설정된 API로, 기존 출력 생성에서는 DOCX가 설정된 OnlyOffice로 전달됩니다. 레이아웃 단독 테스트는 번역 API를 사용하지 않습니다.

## 테스트

```powershell
python -m pytest tests -q
```

테스트는 임시 폴더에서 PDF를 생성하며 원문 재삽입, 배경 보존, 긴 교체문의 원문 유지,
회전 텍스트·스캔 페이지 처리, API 업로드·재생성·다운로드·입력 검증을 검사합니다.


## 표·이미지 처리 (새 번역 비교)

- `enhanced.py`: 원본 글자 + 도형 글자 OCR + 이미지 문자 검출 → 셀/문단 구성.
- `ocr_review.py`: 이미지 글자는 비율을 유지한 여백을 붙여 읽고, 도형과 원래 텍스트가 섞인 영역은 원문을 보완합니다. 문서에 인쇄된 지시는 데이터로 취급합니다. 작은 이미지의 숫자·고유명사·서명은 오독할 수 있어 OCR 결과는 검토 대상으로 표시합니다.
- 같은 배경·색상·크기의 인접 이미지 줄은 문단으로 묶습니다. 이웃 영역의 여백은 중간 지점에서 나눠 번역문이 서로 겹치지 않도록 합니다. 경계가 없는 표 열을 페이지 끝까지 임의 확장하지 않습니다.
- 이미지 OCR은 페이지당 450dpi 이미지를 한 번 만들고 셀/문단별로 잘라 최대 6개 영역씩 요청합니다(동시 요청 4개). 전체 문서 이미지를 먼저 메모리에 모으지 않고 페이지 단위로 처리합니다. 도형/네이티브 혼합 원문 보완은 별도 220dpi 페이지 이미지 한 장을 사용합니다.
- 응답 ID 누락·중복·잘림은 해당 영역을 개별 재시도합니다. OCR 이미지 준비와 인식 완료 진행률을 별도로 표시합니다. 요청 횟수 감소가 같은 비율의 시간 단축을 보장하지는 않습니다.
- 동일 PDF 재업로드는 파일 SHA-256 기준 `data/_cache/<hash>/`의 분석·OCR·번역 캐시를 공유합니다. OCR은 모델·프롬프트·좌표·방식 버전을 검사하며, 새 방식의 캐시가 있으면 페이지 이미지도 만들지 않습니다. 이전 방식의 OCR 캐시는 보존하지만 방식이 바뀐 최초 실행에서는 새로 인식할 수 있습니다.
- 원본 텍스트는 삭제하고, 이미지/도형 글자는 해당 영역의 배경색으로 지운 뒤 번역문을 삽입합니다. 표 선을 별도 보호합니다. 페이지 전체를 이미지로 바꾸지는 않습니다.
- 복잡한 사진 배경은 균일색 복원으로 안전하게 처리할 수 없어 원문 유지/검토 필요로 표시합니다. 인식 불가·공간 부족도 조용히 성공 처리하지 않습니다.
- 기본 최소 크기는 3pt, 최소 비율은 40%입니다. 작은 도표를 위한 하한이며, 5pt 미만은 검증 경고를 표시합니다. 가독성이 중요하면 UI에서 하한을 높이세요. 작은 원본 영역에 긴 번역을 넣으면서 크기까지 동일하게 보존하는 것은 불가능할 수 있습니다.
- 번역문과 같은 고유명사/기호는 원본을 유지하며, 번역 배치 수와 구분합니다.

OCR 모델 설치:

```powershell
./setup-ocr.ps1
```

기본 한국어·영어를 설치합니다. 다른 원문 언어는 `-Languages jpn,eng`처럼 추가합니다. 모델 출처: https://github.com/tesseract-ocr/tessdata_best (Apache 2.0).

실제 API를 사용하는 회귀 검증은 별도 명령입니다. 일반 pytest는 API를 호출하지 않습니다.

```powershell
../backend/.venv/Scripts/python.exe check_real_pdf.py 입력.pdf data/real-check --pages 4
```

이 명령은 원문 영역을 설정된 외부 API로 전송하고 비용이 발생합니다. 생성한 PDF는 검증 보고서와 함께 시각적으로 확인해야 합니다.
